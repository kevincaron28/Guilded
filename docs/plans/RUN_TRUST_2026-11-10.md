## 1. What is true today

- Every Guilded client in a party records the run itself (own clock, own boss kills, shared run id from
  the elected recorder). When the group leaves the dungeon each one sends the run to the guild (`SUM`);
  guildmates' addons keep a copy with `reporters` = the game-reported senders who were in the run.
- A **signed-in** companion uploads its own runs and relays guildmates' runs a participant sent
  (`relayableDungeonRuns`). These uploads are tied to a Discord member (`DungeonRun.importId`).
- An **unsigned** companion (device key, 9.1.0) uploads only runs "its own" characters played
  (`runsOfDevice`). The characters are the ones the same anonymous device declared, so the check proves
  nothing: any key can name any 12 characters and post runs for them (audit 2.1).
- Since #715 an unsigned companion never relays a guildmate's run, so a guild with no signed-in
  companion never gets an addon-only member's run.
- Everything in a saved file is editable. The only things the bot can really tell apart are **who
  uploaded** (which device key, which member credential) and **what the server already knows** (the
  officer-synced roster, linked characters).

## 2. Options

**A. Sign runs in the addon.** A per-character secret signs each run. Rejected: an addon cannot keep a
secret (the key sits in the same editable saved file and in readable Lua), and addon-only members have
no way to register a key.

**B. Sign-in required for runs (audit Q2c).** Only member credentials upload runs. Safe and simple, but
it is the opposite of the request: the companion stops being zero-setup, and a guild without a signed-in
companion syncs nothing.

**C. Corroboration ledger on the bot (chosen).** The bot stops asking "who uploaded this?" and asks "how
many independent sources say this run happened, and is anyone in it known?". Anonymous devices may send
every run their addon holds, first-hand or heard from a guildmate; each upload is a *witness statement*
kept in a ledger. A run is stored and scored only when the statements are enough. Nothing new is asked
of the member, the addon needs no secret, and an edited file is one statement like any other.

## 3. The model

### Sources

| Source | What it is | Weight |
| --- | --- | --- |
| Member credential, own run | Signed-in companion, uploader's character in the party | Accountable: stores alone (unchanged) |
| Member credential, relay | Signed-in companion carrying a run a participant sent in game | Accountable: stores alone (unchanged) |
| Device, first-hand | Unsigned companion; one of the device's reported characters is in the party | One statement, speaking for that character |
| Device, relay | Unsigned companion carrying a guildmate's run; `reporterNames` holds a participant | One statement, speaking for that reporter |

A device statement "speaks for" one party character (its **voucher**). Two statements are independent
only when they come from **different device keys and speak for different party characters**: a relay of
A's run by B's PC and A's own upload are the same statement twice (both rest on A's addon).

### Fingerprint and tolerances

Two statements describe the same run when all of these hold (same rule the import already uses for
observer copies, plus the boss order):

- same dungeon (`instanceId`) and difficulty;
- end times within **120 s** (everyone sees the final boss die at the same moment; clocks are the
  game server's);
- start times within **600 s** (a late joiner's addon starts later; `ACTIVE` aligns most of them);
- at least **two** party names in common by first name (one for a solo run, all of a duo);
- the order of the boss kills both saw is the same (a statement may hold fewer kills, never a different
  order).

The run id is not part of the fingerprint (two recorders can pick different ids); statements with the
same id that fail the fingerprint are a conflict and never promote each other.

### Decision for a run that only anonymous devices sent

1. **Already stored** (any id that matches the fingerprint): never changed by a device. The device gets
   the receipt. If the stored run was `device` trust and this is an independent statement, the run
   becomes `witnessed`.
2. **Witnessed**: two independent statements agree → stored and scored through the normal import
   (`trust = witnessed`), using the oldest first-hand statement and the time it was first received.
3. **Anchored**: one statement, and its voucher is in the officer-synced roster (`GuildRosterEntry`,
   `inGuild`) or is a linked character of the server → stored and scored (`trust = device`).
   A relay additionally needs the run to be at most 30 days old (same as the member relay).
4. **Pending**: anything else is kept in the ledger with a reason the member sees ("Waiting for a
   second player's addon to confirm it"). It is not a run anywhere: no board, no points, no post.
   It promotes itself the moment rule 2 or 3 becomes true (a second upload, an officer roster sync, a
   link), judged with its original reception time so the season upload window is not lost.
5. **Expired**: a pending run 30 days past its end is answered "Not confirmed by a second player" and
   the addon stops waiting.

Member-credential uploads keep today's path. When one brings a run that a device stored or holds
pending, the normal import stores or merges it and the run is `witnessed` (pending statements for it are
closed).

### Limits that bound a forger

- Single-statement (`device`) runs: at most **20 per device per day** (counted in the ledger, survives
  a restart). Beyond that they wait as pending.
- Pending statements: at most 200 per device; relayed runs at most 25 per upload.
- A device never edits, merges into or adds players to a stored run.
- T7: unclaimed devices idle 90 days expire; reported characters are capped per guild; registrations
  are limited per IPv6 /64; a member sees and revokes claimed devices.

### What an edited saved file can and cannot do

| Attack | Result |
| --- | --- |
| Invent a run for invented or unknown characters | Pending forever, then expired. Never on a board. |
| Invent a run naming real roster members (one key) | Stored as `device`: guild boards only, capped at 20 a day, flagged for officers, never public, removable with the existing officer tools. This is the residual risk, the same reach a guild member's own companion has today, now without the public boards. |
| Two keys on one PC agreeing with each other | Both statements must speak for different party characters, and unknown characters still do not anchor. With roster names it reaches `witnessed` on the guild boards; it still cannot reach the public boards (next section). |
| Replay an old run under a new id | Fingerprint matches the stored run: a copy, nothing new. |
| Change the time or party of a real run after others uploaded | Stored run is never touched; the edited copy is a conflict and stays out. |
| Add oneself to a guildmate's real run | Devices cannot add players to a stored run. |

## 4. Guild boards and public leaderboards

| | Guild boards, points, posts | Public leaderboards (`publishGuildRuns`) |
| --- | --- | --- |
| Member upload (own or relay) | Yes | Yes (existing #203 evidence rules) |
| `witnessed`, at least one member source | Yes | Yes |
| `witnessed`, devices only | Yes | **No**: anonymous keys are free, two prove little publicly |
| `device` (anchored, one statement) | Yes | **No** |
| Pending | No | No |

So the public boards never rank a run that only anonymous installs vouch for; it joins them as soon as
any signed-in companion (the member's own, a guildmate's relay or an officer's) brings the same run.
The #203 rules (frozen season rules, evidence, presence) are unchanged and still apply on top.

## 5. Replay, duplicates, solo and duo

- **Replay / duplicates**: one ledger row per (server, run id, device); a repeat only refreshes it.
  Stored runs are found by id first, then by fingerprint, so a second id for the same clear is a copy.
- **Solo**: one party member, so two independent statements are impossible. A solo run counts only
  anchored (the character is in the roster or linked) or from a member credential.
- **Duo**: both names must match; witnessed needs both players' PCs, otherwise anchored.
- **Party with one addon user**: same as solo for witnesses; anchored by that player.

## 6. How fast an addon-only member's run appears

The game writes saved files only at `/reload` or logout, so the fastest possible path is:
A leaves the dungeon → A's addon sends `SUM` → guildmate B (any companion, signed in or not) hears it →
B's next `/reload` or logout → B's companion uploads within a minute. If A is in the synced roster the
run is on the guild board then. Before this change that worked only when B was signed in with Discord.
A replays at each login for 30 days until someone confirms (`ACK`), and catch-up passes it between
Guilded clients, so one companion anywhere in the guild is enough.

## 7. What the member sees

`/guilded dungeon status` (and `/gdungeons status`): "Saved runs: N (W waiting to reach Discord)", and
when some are held, one more line: "H received by Discord, waiting for a second player's addon to
confirm" with the reason of the newest one. The run window shows the same note. A pending run is **not**
marked synced, so the addon never tells its author "my bot has your run" (`ACK`) for it. Stored runs
show as today, with the usual not-scored reason when there is one.

Officers see pending counts in the device answer only for now (no new command; `/setup` text budget).

## 9. Not covered, needs a real client

- Two PCs, both unsigned, same run: second upload promotes the pending run (when neither character is
  in the roster).
- Addon-only A, unsigned B not in the run: B's reload carries A's run; A's next replay gets `ACK`.
- A guild renamed in game: the device lands in the right server and officers get the alias line.
- Production counts (how many stored runs came from devices so far) were not read; existing device
  runs have `trust = NULL` and are treated as before (public publishing included). A back-fill query is
  in the migration as a comment for the owner to decide.

## 10. Season 1 exception (owner, 10 November 2026)

"For estimates and this season can we have anonymous-only runs uploaded and turn it off for season 2."

- `countsDeviceOnlyRuns` (`run-trust.ts`): on until an official season numbered 2 or later has started
  (`OfficialSeason.number`, the calendar `/guilded-season season2-activate` writes). No stored flag, no migration:
  the Season 2 activation flips it by existing. Season rules (#203) are a validated, hashed snapshot, so a flag was not added to them.
- During Season 1 a run with a single anonymous source and no known party member is stored (`trust = 'device'`),
  receipted, and published like before #725. The 20-a-day cap and "a device never changes a stored run" still apply.
- From Season 2: pending with a reason, and runs ended after Season 2 starts with a `trust` stay off the public boards
  (`publishGuildRuns`); Season 1 runs already published stay.
- Runs pending since the #725 deploy: the companion resends every waiting run on each upload, so they are stored
  on that device's next upload. Pending runs of a device that never uploads again stay pending (no job).
