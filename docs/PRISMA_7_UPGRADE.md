# Prisma 7 upgrade: runtime changes, checks, rollback (21 October 2026)

Branch `fix/prisma-7-upgrade`: Prisma 6.19.3 → **7.10.1** for the bot (`@prisma/client`, `prisma`,
and the new `@prisma/adapter-pg`). Prisma 8 is still a release candidate, so this stays on 7.
**Not deployed.** No schema change and no new migration. `package.json`'s version is unchanged,
so nothing is announced.

Two commits, so the second can be reverted alone:

1. **Prisma 7 + node-postgres adapter** (`2364c24`): dependencies, `prisma.config.ts`, the URL
   translation in `src/database.ts`, scripts that built their own client, `postinstall`.
2. **New `prisma-client` generator** (`b36667e`): the deprecated `prisma-client-js` generator is
   replaced. The client is now generated TypeScript in `src/generated/prisma/` (gitignored), and
   every `from "@prisma/client"` import points there. The backup lists tables from
   `Prisma.ModelName` (the new client has no `Prisma.dmmf`).

## What changes at runtime

| | Prisma 6 (live) | Prisma 7 (this branch) |
|---|---|---|
| Talks to PostgreSQL through | Prisma's Rust query engine (native library) | `node-postgres` (`pg`) through `@prisma/adapter-pg`; queries are planned by a WebAssembly compiler |
| Reads `DATABASE_URL` | the engine reads `connection_limit`, `connect_timeout`, `pool_timeout`, `sslmode`, `sslcert`, `sslaccept` | `poolSettings()` in `src/database.ts` translates those same parameters into `pg` settings |
| Pool size | `connection_limit` from the URL, else 8 | the same |
| Connect / wait-for-a-connection timeouts | `connect_timeout`, `pool_timeout` (30 s added when missing) | one `pg` timeout: the larger of the two, 30 s when missing |
| Idle connections closed after | 5 minutes | 5 minutes (`pg` alone would close them after 10 s) |
| TLS to Aiven | `sslmode=require`, `sslcert=<Aiven CA>`, `sslaccept=strict`: certificate and host name checked against Aiven's CA | the same check: the CA file is read at startup, `rejectUnauthorized: true` |
| `npm run db:update` (`prisma migrate deploy`) | URL from `schema.prisma` | URL from `prisma.config.ts`. Migrations still go through Prisma's own engine, which reads the URL exactly as before |
| Client generated by | `npm install` (built into `@prisma/client`) and `npm run db:update` | the same: `package.json` now has `postinstall: prisma generate` because Prisma 7 dropped its own |
| Memory, measured on this PC (one process, one query, local test server) | about 80 MB resident | about 120–170 MB resident (both generators) |
| Time to the first query, same measurement | ~0.1 s import + ~2 s engine start | ~0.25 s import + ~0.2 s |

Why translate the URL? `pg` reads the same URL differently. It ignores `connection_limit` and the
timeouts, reads `sslcert` as a *client* certificate, and treats `sslmode=require` as "verify
against public certificate authorities", which do not sign Aiven's certificate. Passed unchanged,
the production URL would not connect. With the translation, **neither `.env.local` (PC or Oracle)
needs to change**, so rollback stays a code-only revert.

Other differences:

- A connection the server drops while idle is replaced on the next query, as before. It is now
  logged as one line: `Database connection closed while idle: ...`.
- Connection failures are still `PrismaClientKnownRequestError` (`P1001 Can't reach database
  server`, checked here), so the bug reporter still reports them as errors.
- Scripts that built `new PrismaClient()` themselves (`verify-postgres`, both beta-season
  scripts, `release:ledger-check`) use `createPrismaClient()` from `src/database.ts`, because
  Prisma 7 refuses a client without an adapter. `release:ledger-check` now runs through `tsx`.
- `prisma.config.ts` (new, repository root) loads `.env` only, as Prisma 6's CLI did. The npm
  scripts still go through `scripts/with-env.mjs` (`.env.local`, then `.env`, and `DIRECT_URL`
  for migrations).
- `deploy/update.sh` and `setup-server.sh` keep `src/generated` through `rsync --delete`. The
  running bot loads some modules lazily, so it must still find the client until the restart
  regenerates it.
- Not carried over: client-certificate parameters (`sslidentity`, `sslkey`) and `?schema=`. No
  Guilded URL uses them. `sslmode=prefer`, or no `sslmode`, now means no TLS, as it does for
  `pg`. Prisma 6 tried TLS first.
- `pg` prints one deprecation warning under concurrent load ("client.query() when the client is
  already executing a query"). It comes from Prisma's own query interpreter, not Guilded code, and
  is harmless with `pg` 8, which `@prisma/adapter-pg` requires.

## Before any deploy: try it against a copy of production

Never against the live database, except the step marked read-only. Never start the bot
(`npm run dev`, `start-bot.bat`): Oracle already runs it.

1. **CI.** Push the branch and open the pull request. Both `Guilded quality` jobs must pass; the
   first runs `npm run test:postgres` on PostgreSQL 16, with a dump/restore rehearsal.
2. **Fresh backup.** On Oracle, as in `docs/V5_0_RELEASE_HANDOFF.md` step 4: a custom-format
   `pg_dump`, stored outside the checkout with mode 600, then checked with `pg_restore --list`.
3. **Disposable copy.** Restore that dump with `pg_restore --no-owner` into a local PostgreSQL 16
   that is not production, under a database such as `guilded_prisma7_copy`. Either the
   repository's `docker compose up -d postgres` or a PostgreSQL 16 install will do.
4. **Migrations on the copy.** In a branch checkout, with `DATABASE_URL` set in the shell to the
   copy only: `npx prisma migrate status` must report the database up to date with 88
   migrations, and `npx prisma migrate deploy` must apply nothing.
5. **The same data through both versions.** Run `npx tsx scripts/db-snapshot.ts snapshot <empty
   folder>` twice against the copy: once in a checkout of `main` (Prisma 6) with
   `scripts/db-snapshot.ts` copied in, and once in the branch. Then, in the branch, run
   `npx tsx scripts/db-snapshot.ts compare <main file> <branch file>` and expect "Identical". Any
   table it names means stop. The output lists table and field names only, never values, so it
   is safe to send.
6. **Read-only TLS check against Aiven** (the owner's call; it only reads). On the PC, in the
   branch, with the normal `.env.local`: `npm run release:ledger-check` must print "Ledger event
   references are unique." A certificate error, `P1010` or `P1011` means the CA translation does
   not work on that machine: stop and stay on 7.3.0's Prisma 6.
7. **Before deploying,** run the same read-only check on Oracle from a branch checkout. Its
   `.env.local` points at `/etc/guilded/aiven-ca.pem` (see `docs/AIVEN_MIGRATION.md`).
8. **Note the bot's memory now** (`systemctl status guilded`, the `Memory:` line). Expect it to
   rise by roughly 50–90 MB; the cap is `MemoryMax=700M` on a 1 GB VM.

## Deploy notes (when it ships)

- No `.env.local` change and no migration. `deploy/update.sh` sees the new `package-lock.json` and
  runs `npm ci`, whose `postinstall` generates the client. The service's `npm run db:update`
  generates it again before start.
- Watch the first start: run `journalctl -u guilded -n 100` and look for `P1001`, `P1010` or TLS
  errors and for `Database connection closed while idle`. Then check `/health`, `/report ping`,
  and memory with `systemctl status guilded`.
- The next daily backup (`backups/quebec-gold-*.json.gz` on Oracle) should list the same 94 tables.

## Rollback

Code only: there is no data, schema or environment change to undo.

- Before the merge: close the pull request.
- After a deploy: revert the merge on `main` (`git revert -m 1 <merge commit>`), push, and deploy
  as usual (`redeploy-oracle.bat`). The lockfile change makes `update.sh` run `npm ci`, which
  reinstalls Prisma 6, and `npm run db:update` regenerates the Prisma 6 client. This upgrade never
  touches `_prisma_migrations`, so Prisma 6 reads the same history. A leftover `src/generated/`
  folder on the server is ignored by Prisma 6.
- To keep Prisma 7 but drop only the generator change, revert `b36667e`.

## Found while doing this (not changed)

- The local `.env.local` sets `connection_limit=5`, and `docs/AIVEN_MIGRATION.md` records the same
  on Oracle. The URL wins over the default, so production most likely still runs on **5**
  connections, not the 8 that 7.2.1 announced. Removing `connection_limit` from the URL (or setting
  it to 8) would apply 8. That is an environment change for the owner to decide separately; it
  behaves the same before and after this upgrade.
- When the bot does not come back, `deploy/update.sh` suggests `git checkout <previous commit> &&
  sudo bash deploy/update.sh`. That cannot work: the script refuses a checkout that is not on
  `main`, and it would fast-forward to `origin/main` again. Reverting on `main` (above) is the
  path that works.
